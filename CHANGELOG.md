# Changelog

All notable changes to the LibKa Design Platform are listed here, newest first. Versions follow [Semantic Versioning](https://semver.org/).

## 2.0.3 (2026-11-09): AI provenance, seven new blocks, a new LibKa Studio layout

- **AI provenance, the front matter key `ai` and the attribute `ai=`:** a document says how AI took part, `ai: ai-assisted` (AI helped with a person's text) or `ai: ai-generated` (AI wrote it); the long form puts the use under `use` and adds, optionally, `reviewed-by` (who checked it and holds editorial responsibility), `approved-by`, `tool`, `date`, `checked` and `label` beside it (`ai:`, then `use: ai-generated` and `reviewed-by: Ann Novak` on the lines under it, indented); a block marks the parts AI wrote with `ai=generated` or `ai=assisted`. It is the author's declaration, recorded in the signed manifest (`provenance`, and each marked block in `ai`). A visible label is shown only when the author turns it on (`label: true`): one sentence under the title on the web page, in the PDF, in the Word file and on the title slide ("Created with AI tools. Reviewed and approved by …"), and an "AI-generated" badge before each marked block nobody is named as having reviewed. Nothing is blocked: `lint` reminds the author when AI-generated content names no reviewer and shows no label, since AI-generated text that informs the public on matters of public interest needs one or the other (EU AI Act, Article 50(4)), and only the author can tell whether a document does. The skill and the MCP server mark what AI writes (never with an invented reviewer); LibKa Studio has the fields in the document's properties. Malformed values are reported (`ai-invalid`).
- **Changed: AI summaries follow the same rules.** `:::summary{source=ai}` counts as `ai=generated`. A missing `reviewed-by` is a reminder, no longer a problem (`summary-reviewer` is gone), and the summary's "AI-assisted, reviewed by …" line is shown only when the document turns the AI label on, now as "AI-generated" with "Reviewed and approved by …". The reviewer is always recorded in the manifest.
- **A new block, `:::byline`, and the front matter key `author`:** one or more people, each with an optional role (`author: Ann Novak`, or a list with `name` and `role`). The authors appear under the title of the web page, the PDF and the Word file and on the title slide of a deck; `:::byline` shows them where it stands instead. Their names are also the page's author metadata, the PDF's author (in its XMP and document information) and the Word file's author, and the signed manifest lists them as declared. LibKa Studio edits them in the document's properties.
- **A new block, `:::download`:** a link to a file named by what it is, with its format, size and, for a PDF, its pages in the link text (`Annual report 2025 (PDF, 2.1 MB, 48 pages)`), and an optional sentence about it. For a file next to the document, `libka build` works out the size and a PDF's pages and copies the file into the output folder, as it does for images; a missing file is reported on its line. The format comes from the file name unless `type` names it; a file on another site needs `type` and `size`. Sizes and page counts are written in the document's language (`2,1 MB, 3 strany`).
- **A new block, `:::revisions`:** a document's revision history as a Markdown table with the columns version, date and change, and optionally author and approved by, recognised by their headings in English or Czech (`Verze`, `Datum`, `Změna`, `Autor`, `Schválil`, `Schválila` or `Schválení`). Dates are checked (YYYY-MM-DD), the same version twice is reported, and the rows must run newest first or oldest first by date and version. It is a section of its own, like the reference list: a level-2 heading with an anchor ("Revision history" unless its label names it), listed in the contents, over the table on the web page, in the PDF and the Word file (Heading 1), and a slide of its own that continues on the next one when the table is long. A heading of the author's own right above it is reported (`revisions-heading`). The signed manifest lists each version with its date and who approved it, as declared.
- **A new block, `::::decision`:** a decision record as a section of its own. Its title states the decision; `status` (proposed, accepted, rejected, superseded) is shown as a word on a badge, with `date` and who decided (`by`), both required once a decision is taken. A sentence stating the decision may come first, then `:::context` (required), `:::options` (which may hold a `:::comparison`) and `:::consequences`, always shown in that order under their own subheadings. Like a release, each decision is a level-2 heading with an anchor, listed in the contents and its own slide; in the Word file it is Heading 1 with each part as Heading 2.
- **A new block, `::::pros-cons`:** the pros and cons of one option. The label names the option; `:::pros` and `:::cons` each hold one bulleted list, shown pros first under the written words "Pros" and "Cons" (in Czech "Výhody" and "Nevýhody"), side by side where there is room and stacked on a phone. Both sides are required. Several options are several blocks, and a decision's `:::options` may hold one per option. In the Word file each side is a shaded panel with its word and a bulleted list.
- **A new block, `:::flow`:** how a process runs, as 2 to 6 numbered stages in a row joined by arrows drawn in CSS (stacked with arrows down on a phone), one list item per stage. `shape=cycle` marks a process that starts again, and the return to the first stage is written out under the stages ("Then it starts again: …"; in Czech „Pak vše začíná znovu: …“), never shown by an arrow alone. In the Word file it is the process's name and a numbered list. Instructions the reader carries out stay `:::steps`.
- **A new block, `::::matrix`:** points sorted into four quadrants, read left to right, top row first. `type=swot` fills in the quadrants' names (Strengths, Weaknesses, Opportunities, Threats; in Czech "Silné stránky", "Slabé stránky", "Příležitosti", "Hrozby"); `type=grid` names each `:::q` and says in words what changes across (`x=`) and down (`y=`). Each quadrant is a group named by its visible name; the axes are written beside the grid and read before it. A 2 × 2 grid on the web page, in the PDF and on slides, stacked on a phone; in the Word file a 2 × 2 table under a header row with the title.
- **Changed: dates are written in the document's language, and the new front matter key `date-format` chooses how.** The source keeps YYYY-MM-DD; the web page, the PDF, the slides and the Word file write every date (under the title, the review dates, a decision, a release, the revision history and a timeline's days and months) as `long` "28 October 2026" / "28. října 2026" (the default), `short` "28/10/2026" / "28. 10. 2026" or `iso` "2026-10-28", the way they were written before. The `<time datetime>` and the manifest keep ISO. A misspelt value is reported (`date-format-unknown`) with the nearest one as a fix; the Studio has the key among the document's fields.
- **Fixed: a key figure in `:::metrics` no longer breaks inside.** On a phone "184,000" broke into "184,0" and "00", and on a wide page a four-figure row broke "1,234,567". The columns are now at least as wide as the block's longest figure, and the figures shrink to fit their tiles (down to 1.75rem before the tiles stack); a figure breaks only at a space, and its digit groups stay together in every language ("184 000").
- **Changed: `libka build` leaves only this build's outputs.** It removes the document's own outputs from an earlier build that it did not make again (the slides, say, after a build without `deck`) and says so on a "removed" line; nothing else in the output folder is touched. Its output heads the web page's checks "web:", as it heads the slides' "deck:", lists the conformance reports among the files written, and shows the PDF/UA-2 result, which is recorded and never required. The MCP server's `libka_build` returns the conformance reports and the removed files too.
- **Changed: the conformance report (`.conformance.md`) is written in the document's language**, English or Czech. The WCAG criteria keep their English names, since there is no official Czech translation of WCAG 2.
- **Changed: the automatic contents come after the opening text**, right before the first `##` section, on the web page and in the Word file; they stood above it. The PDF keeps its bookmarks instead.
- **Changed: the Word file no longer ends with "Diagram sources".** A diagram is its picture and its description; the Mermaid source stays in the LibKa Markdown file and on the web page.
- **Fixed: the PDF's last page no longer holds only the footer line.** The end of the content moves to the last page with it.
- **Fixed in LibKa Studio: text such as "16:9" stays as written in the visual editor.** It showed as "16" and a ":9" chip, and "a:b" was saved as `a\:b`. Only the inline directives LibKa knows are read as directives now, as in the build, and typed text is escaped only where it would become one of them.
- **Fixed in LibKa Studio: Bold, Italic, Code and Strikethrough show as on only when all of the selected text has them.** A paragraph with a little code in it showed Code as on. A click (or Ctrl+B, Ctrl+I, Ctrl+E, Ctrl+Shift+X) on a partly marked selection now marks all of it, and a second click removes the mark.
- **Fixed in LibKa Studio: Preferences and the accessibility statement open at their top**, with the focus on their heading; they opened scrolled to the Close button at the end.
- **Fixed in LibKa Studio: an edit inside a block that holds other blocks changes only what you edited.** Typing a letter in one card of `::::cards`, in a decision's options or in one tab wrote the whole block anew in LibKa's own style: blank lines appeared between its parts and quoted values lost their quotes (`href="#code"` became `href=#code`). Now the block's opening and closing lines, its other parts and the space between them stay as written, at every level, and only the edited part is written anew. A changed setting rewrites only its block's opening line. The blank lines around an edited block stay as they were too. A part added with "+" is spaced like the others.
- **Changed in LibKa Studio: a calmer layout.** Dark mode, high contrast, the interface language, Split, focus mode and Preferences are in a new **View** menu. The editor has one toolbar row in the same order in every mode: the format buttons, **+ Block** and Visual | Source; in Source the format buttons stay, unavailable, with the reason under them. **+ Block** replaces the quick blocks and "More blocks": one block picker, with search in English and Czech, the recent blocks first, a small drawing of every block and a close button, which inserts in either editor ("/" on an empty line opens the same picker in Visual). The versions inside moved from the status bar to Help → About, and help text shows no Markdown marks.
- **Changed in LibKa Studio: modes and panes.** A switch in the top bar chooses the mode: **Write** (the editor with its preview, A4 by default, scaled to fit), **Blocks** (the block catalog on the left, the selected block's properties on the right) or **Focus** (the page alone, below); Alt+1, Alt+2 and Alt+3 switch them, and each mode remembers its own panes. The pane on the right shows **Preview**, **Checks** or **Properties** (formerly the Inspector), can be closed (a strip of its tabs stays at the edge) and is resized with the divider by dragging or by the arrow keys. The pane on the left, opened from the strip at the left edge, holds the **Catalog** (every block with a small drawing: click to insert, or drag; it replaces the side palette and its preference) and the **Outline** (the headings, or every block as a tree). The document's title is a menu with **Versions…** (formerly the History tab) and Document properties. F6 and Shift+F6 move between the top bar, the panes, the editor and the status bar; each region is a landmark. At 1024 px the editor and the pane on the right sit side by side, with nothing below them.
- **Changed in LibKa Studio: one Checks list.** The problems in the source, what Guard finds in the outputs and the lint hints are one list, by place in the document ("Before you start › Figure"). Each item says where it fails (Source, Web and PDF, Slides, Word) and whether it must be fixed or is advice; advice (a horizontal rule no output shows, a comment in a Marp deck) never counts and never stops anything. The same finding on the web page and the slides is one item, and a problem in the source and Guard's finding of the same thing (missing alt text, a missing caption) are one item with the problem's fix, so "8 to fix" is now "4 to fix" when four things are wrong. Filters: All, or This block (the selected block); a block's problem mark in the visual editor opens Checks on that block. Each item goes to the text, a finding in the web page or the slides can be shown in the preview, and the checks' own numbers, as `libka check` counts them, are under Details. Guard's findings are linked to their block by the source line LibKa Studio marks on its own render of the page; `libka build` never writes these marks and exports leave them out. A change made just after the slides were fitted no longer lets Guard check the next slides before they are fitted (Checks briefly showed overflows that the fitting resolves).
- **Changed in LibKa Studio: blocks look like their output while you write.** In the visual editor a matrix shows its four quadrants two by two with its axes, a flow its stages in a row with arrows (a cycle says it goes back to the start), pros and cons and do and don't side by side with ✓ and ✗, cards in a grid, key figures as tiles with the figure large, a timeline as dots on a line with the current milestone marked, and steps as numbered circles. Each tab's name is drawn as a tab over its panel (every tab stays editable), an accordion's questions as rows with their answers under them, a comparison's recommended column is outlined with its badge and yes, no and partial are marked ✓, ✗ and ◐, a decision shows its status, date and who decided above its context, options and consequences, a release its date and each kind of change under its own colour, and a UI specimen its buttons, fields and badges drawn as components. A narrower editor stacks them, as the outputs do. A "+" at the end of each adds one more stage, step, figure, milestone, pro, con, card, do-and-don't pair, tab or question, up to what the block can hold (a flow six stages, the key figures four); the block menu (Shift+F10) does the same from the keyboard.
- **Changed in LibKa Studio: Focus, the layout in View, and phones.** **Focus** is now the page alone: no toolbar, panes or status bar, the text in a readable column a little larger, and a small dock under the page with **+ Block**, the **Checks** count and **Exit Focus** (also Ctrl+Shift+F; Alt+1 goes to Write). Formatting stays on its keys. **View** sets the width of the pane on the right in one click (**Narrow**, **Medium**, **Wide**, besides dragging the divider or its arrow keys) and has **Reset this mode's layout**, which brings back the mode's own panes and the default width. On a phone (narrower than 900 px) the top bar is one row: the Studio's dot, the readiness status, Documents and **⋯**, which holds the modes, the document's menu, View, Export and Help, with the line, the word count and the saving state at its top. **Write**, **Preview**, **Checks** and **Outline** moved to a bar at the bottom of the screen, within thumb reach, with an icon and a name each; it is part of the layout, never over the text, and it hides while the on-screen keyboard is open.
- **Changed in LibKa Studio: the document's menu, Export and plain names.** The document's title is a menu with **Rename…** (the title and the file name in one dialog), **Duplicate** (the copy opens at once), **Save now** (Ctrl+S), **Save a version…**, **Versions…** and **Document properties**; menus show each command's keys. **Export** replaces File: **Web page (.html)**, **Slides (.html)**, **Word (.docx)**, **PDF (print…)** and **LibKa Markdown (.md)**, then **Save to a folder…** and **Download everything (.zip)**, and **Choose outputs…**, which opens Properties where the outputs are now set (one place instead of two). New document, the example, Import and Open folder are in Documents. **Properties** names every setting in plain words, in English or Czech ("Next review", "Tab name"), with the key the file uses beside it (`next-review`); the block catalog lists the same names.
- **Changed in LibKa Studio: the block bar.** When the cursor is in a block (a callout, a process, a decision, a figure), the toolbar shows a bar for it after **+ Block**: the block's name, its most used setting (a callout's kind, a decision's status, a process's shape, a matrix's or a chart's type; a figure's alt text, "Write alt text" until it has one), **+ Stage**, **+ Card** and so on up to what the block can hold, **Move up** and **Move down**, **⋯** with the whole block menu, and **Properties**. Plain text has no bar, and the toolbar keeps its height either way, so the text never jumps. In Focus the bar is in the dock under the page; on a phone it is a row above the bottom bar (on a 390 px phone a figure's bar takes two rows). Which setting a block offers is marked in the block registry (`quick`, at most one per block).
- **Changed in LibKa Studio: choices named in English too, a top bar that keeps the title, menus that leave no sliver.** In English, the block bar and Properties now name a choice's values in words ("Info", "Author–date", "Sections and subsections"), as the Czech interface already did; the file still writes the value (`info`). The names are in the block registry (`VALUE_LABELS_EN`, next to the Czech ones), and a test keeps every value named in both languages. Where the top bar is tight (a Czech interface at 1440 px and below, any language below 1366 px), "Saved in this browser" shows as "✓ Saved", then as ✓ alone, and the file name gives way, so the document's title keeps its room; the whole sentence stays in the tooltip and for screen readers. Below 1440 px the Czech readiness „Připraveno k publikaci“ shows as „Připraveno“; the whole phrase stays the button's name. An open menu in the top bar never leaves a control under it a sliver smaller than 24 px (WCAG 2.5.8): it moves aside by a few pixels until each control is covered or keeps 24 px. Under View at 1024 px it left 10 px of the editor's Source button. Switching from Source back to Visual (or ending Split) now shows the place you were at; the visual editor opened at the top of the document with the cursor further down. The example document ("Writing a LibKa manual") gives the public commands (`npx -y @libka/cli build guide.md`) instead of the repository's own. On a touch screen, a block inside another (a paragraph in a callout) shows its handles only when it is selected; always shown, they sat over the outer block's edge.
- **New in LibKa Studio: Present.** View → **Present** (F5) shows the current deck full screen from the first slide, **Present from this slide** (Shift+F5) from the slide the cursor is in, and the Preview's Slides view has a **Present** button. It is the deck you would export, with its notes, overview, dark theme and high contrast; P opens the presenter view (the notes, the next slide and a timer) in a second window that follows the slides, and Esc or **End** returns to the text, with the Preview on the slide you ended on. In the Preview, the deck's own full-screen and presenter-view buttons (and F and P) now start Present; before, they did nothing useful there. The deck runtime has a new `libkaDeck.link()`, which a page holding a deck in a frame uses to pair it with the presenter view's window.
- **Changed: the message for an unknown block names the likely block, or the three closest, instead of all of them** (`block-unknown`: "unknown block "calout": did you mean :::callout?").
- **Changed: a Marp deck is named as one.** A document with `marp: true` in its front matter gets the problem `marp-file`, which says that LibKa makes slides from `##` and `###` headings, with a fix that removes Marp's keys. `libka lint` now gives a hint, on its line, for every horizontal rule (`---`), which no output shows, and in a Marp deck for every comment, which is not a speaker note there (write `:::notes`); hints never stop a build. The AI skill converts a Marp deck by these rules. In LibKa Studio's visual editor, typing `---` no longer makes a horizontal rule; it stays text.
- **Dependencies:** `mermaid` 12.2.0, `preact` 11.1.0, `@preact/signals` 2.11.4, `prosemirror-view` 1.42.8, `prosemirror-transform` 1.12.4, `@codemirror/view` 6.43.15, `@lezer/markdown` 1.8.1, `docx` 9.15.0, `mdast-util-to-markdown` 2.2.1, `@modelcontextprotocol/sdk` 1.32.2, `zod` 4.6.7, `playwright-core` 1.64.1, `@guidepup/guidepup` 0.39.0, `@guidepup/setup` 0.29.3, `vitest` 5.0.5 and `@types/node` 26.6.6.

## 2.0.2 (2026-10-28): alt text kept whole, the format called LibKa Markdown

- **Alternative text:** an image's alt text keeps text such as `4.5:1`, `16:9` or `10:30`; 2.0.1 dropped everything from the colon on (`4.5:1` became `4.5`) in every output. Captions were not affected.
- **Visual editing:** when a block is changed, its links, captions and alt text are written as they were: `mailto:` and other schemes are no longer written as `mailto\:`, and a caption's `4.5:1` no longer as `4.5\:1`. Blocks you do not change were never affected.
- **The format's name:** the source of a LibKa document is called LibKa Markdown wherever a text names it: the READMEs, the guides, the npm packages' descriptions, the Desktop extension, the MCP server's instructions, the authoring skill and the labels of LibKa Studio in English and Czech. The file stays `.md` and opens in any text editor; only LibKa renders the blocks.
- **The starter's workflow** pins the LibKa Guard action's 2.0.1 and keeps its outputs 7 days instead of 14. Its README (English and Czech) and the Guard action's README say who pays: the workflow runs in your repository, free in a public one, and on your account's Actions minutes and storage in a private one.
- **Wording:** the READMEs say exactly where a problem is marked in a pull request: a problem in the source on its line, a finding in an output on its file. The READMEs and the getting-started guide say the PDF is validated against PDF/UA-1 when Java and veraPDF are installed, and that the Studio runs the page and Word checks while you type; the Studio's accessibility statement speaks of documents that pass LibKa's accessibility checks, where it said accessible documents.
- **Dependencies:** `docx` 9.10.0, `@types/node` 26.6.5 and `@guidepup/setup` 0.29.2.
- **For maintainers:** `publish.yml` waits until npm shows the new version before it lists it in the MCP Registry, and the registry entry's description fits its 100 characters. A push to `main` that changes only documentation runs no tests; in a private repository a push to `main` tests on Ubuntu alone (Actions minutes count there; [`docs/admin/environment.md`](docs/admin/environment.md), "Minutes in a private repository"). `packages.yml` also runs every Monday at 05:30 UTC. CI keeps its artifacts 3 days (`check`) and 1 day (`packages`) instead of 14.

## 2.0.1 (2026-10-13): images in builds, the starter on the Guard action

- **Images in a build:** gallery images are copied with the outputs, as figures always were (they were left out, so a gallery built into another folder showed no pictures). An image outside the document's folder (`../images/a.png`) is copied into the output folder, under `_up/` for each level up, and the outputs point at the copy. This fixes a build writing outside its output folder: 2.0.0 copied such an image to the same relative place beside the output folder, which could be anywhere above it. A missing image is reported on its line, so the Guard action marks it in a pull request. An image whose name has a `%` that starts no escape (`100%.svg`) builds; 2.0.0 stopped with "URI malformed" when it built a Word file.
- **The MCP server** refuses `libka_build` with both the document's text and a path, where it used to write the text over the file at that path; a document given by its path is only read.
- **The starter's workflow** checks with the LibKa Guard action: every document in `docs/` is built and checked on every push and pull request, each problem is marked in a pull request (a problem in the source on its line, a finding in an output on its file), and the workflow names the LibKa version it runs; the starter's `package.json` asks for exactly that version. The outputs are kept from `docs/dist/`, beside the documents, and the workflow no longer runs `npm run verify` (2.0.0's ran `npm run check`, `build` and `verify`, and kept `dist/`).
- **LibKa Studio** runs on Preact 11.
- **The Claude Code plugin** has a README that says everything it runs, fetches, reads and writes, and on Windows starts the MCP server with one fixed command line. The guide to AI tools ([`docs/ai-tools.md`](docs/ai-tools.md)) now says what happens to a document's web addresses: the page's Content Security Policy blocks them, and Guard reports each one; 2.0.0 said Chrome loads them.
- **For contributors:** when a test fails, `check.py` shows the failure's own lines (what was expected and what came), not only the end of the run.

## 2.0.0 (2026-10-11): the first public release

LibKa was developed in a private repository up to 2.0; this repository starts with it.

- **Documents:** one Markdown file with LibKa blocks (thirty-five block types at this release, from headings and lists to charts, diagrams and timelines) builds a web page, an A4 PDF, 16:9 slides and an editable Word file; each document chooses its outputs.
- **Guard:** every output is checked (axe-core WCAG 2.2 A/AA in Chrome, text contrast 4.5:1 and 7:1 in high contrast, structure rules, reflow at 320 CSS pixels, slide fit; veraPDF PDF/UA-1 for the PDF; the Word file's structure) and the outputs that pass are signed; a conformance report maps each WCAG 2.2 criterion to EN 301 549. A PDF built without veraPDF is marked as not validated in its manifest, its conformance report and `libka verify`.
- **LibKa Studio:** an installable, local-first web app with visual and source editing, live checks with quick fixes, versions, English and Czech; self-audited against WCAG 2.2 A/AA, with the evidence in `docs/acr/studio.md`. Help, About LibKa Studio gives the licence, the third-party notices and what happens to your documents; `build.mjs --hosted` builds a copy for a web address of its own, whose headers keep a host's statistics script out (`no-transform`); it starts offline on hosts that redirect `index.html` too.
- **Documentation:** the documents in `docs/` are LibKa documents themselves, from [getting started](docs/getting-started.md) to the conformance reports; the block registry carries a Czech example for every block. HTML comments are allowed in documents as notes for editors and are never rendered.
- **Design tokens:** W3C DTCG 2025.10 tokens with light, dark and high-contrast themes, generated into CSS, SCSS and Tailwind themes with contrast gates.
- **AI authoring:** an Agent Skill and an MCP server; AI-written content is checked like any other, and content the document declares as AI-written is listed in the signed manifest. For Claude Code both come as one plugin from this repository's marketplace file; for Claude Desktop the server comes as an extension (`.mcpb`), and the skill as a `.zip` for claude.ai and Desktop ([`docs/ai-tools.md`](docs/ai-tools.md)).
- **Packages:** `@libka/cli` (the `libka` command, with LibKa Studio), `@libka/mcp`, `@libka/tokens`, and `npm create libka` for a new project with an example in English or Czech, npm scripts and a CI workflow. `libka doctor` says what a computer has and what works without each missing piece; a wrong command, a missing value or a missing file is named, and a misspelled front-matter key gets the nearest known one. Each project signs with its own key, and trusts its first key in its own list.
- **Releases:** built from a tag by `publish.yml`: the npm packages with provenance (this first version's packages are published by hand, so they carry no provenance statement), the MCP server in the MCP Registry, and a draft GitHub Release with the Desktop extension, the skill `.zip` and SHA-256 checksums, published after review. Run by hand, the workflow is a dry run by default.
