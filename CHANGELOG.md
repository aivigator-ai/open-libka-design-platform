# Changelog

All notable changes to the LibKa Design Platform are listed here, newest first. Versions follow [Semantic Versioning](https://semver.org/).

## 2.0.2 (2026-10-28): alt text kept whole, the format called LibKa Markdown

- **Alternative text:** an image's alt text keeps text such as `4.5:1`, `16:9` or `10:30`; 2.0.1 dropped everything from the colon on (`4.5:1` became `4.5`) in every output. Captions were not affected.
- **Visual editing:** when a block is changed, its links, captions and alt text are written as they were: `mailto:` and other schemes are no longer written as `mailto\:`, and a caption's `4.5:1` no longer as `4.5\:1`. Blocks you do not change were never affected.
- **The format's name:** the source of a LibKa document is called LibKa Markdown wherever a text names it: the READMEs, the guides, the npm packages' descriptions, the Desktop extension, the MCP server's instructions, the authoring skill and the labels of LibKa Studio in English and Czech. The file stays `.md` and opens in any text editor; only LibKa renders the blocks.
- **The starter's workflow** pins the LibKa Guard action's 2.0.1 and keeps its outputs 7 days instead of 14. Its README (English and Czech) and the Guard action's README say who pays: the workflow runs in your repository, free in a public one, and on your account's Actions minutes and storage in a private one.
- **Wording:** the READMEs say exactly where a problem is marked in a pull request: a problem in the source on its line, a finding in an output on its file. The READMEs and the getting-started guide say the PDF is validated against PDF/UA-1 when Java and veraPDF are installed, and that the Studio runs the page and Word checks while you type; the Studio's accessibility statement speaks of documents that pass LibKa's accessibility checks, where it said accessible documents.
- **Dependencies:** `docx` 9.10.0, `@types/node` 26.6.5 and `@guidepup/setup` 0.29.2.
- **For maintainers:** `publish.yml` waits until npm shows the new version before it lists it in the MCP Registry, and the registry entry's description fits its 100 characters. A push to `main` that changes only documentation runs no tests; in a private repository a push to `main` tests on Ubuntu alone (Actions minutes count there; [`docs/admin/environment.md`](docs/admin/environment.md), "Minutes in a private repository"). `packages.yml` also runs every Monday at 05:30 UTC. CI keeps its artifacts 3 days (`check`) and 1 day (`packages`) instead of 14.

## 2.0.1 (2026-10-13): images in builds, the starter on the Guard action

- **Images in a build:** gallery images are copied with the outputs, as figures always were (they were left out, so a gallery built into another folder showed no pictures). An image outside the document's folder (`../images/a.png`) is copied into the output folder, under `_up/` for each level up, and the outputs point at the copy. This fixes a build writing outside its output folder: 2.0.0 copied such an image to the same relative place beside the output folder, which could be anywhere above it. A missing image is reported on its line, so the Guard action marks it in a pull request. An image whose name has a `%` that starts no escape (`100%.svg`) builds; 2.0.0 stopped with "URI malformed" when it built a Word file.
- **The MCP server** refuses `libka_build` with both the document's text and a path, where it used to write the text over the file at that path; a document given by its path is only read.
- **The starter's workflow** checks with the LibKa Guard action: every document in `docs/` is built and checked on every push and pull request, each problem is marked in a pull request (a problem in the source on its line, a finding in an output on its file), and the workflow names the LibKa version it runs; the starter's `package.json` asks for exactly that version. The outputs are kept from `docs/dist/`, beside the documents, and the workflow no longer runs `npm run verify` (2.0.0's ran `npm run check`, `build` and `verify`, and kept `dist/`).
- **LibKa Studio** runs on Preact 11.
- **The Claude Code plugin** has a README that says everything it runs, fetches, reads and writes, and on Windows starts the MCP server with one fixed command line. The guide to AI tools ([`docs/ai-tools.md`](docs/ai-tools.md)) now says what happens to a document's web addresses: the page's Content Security Policy blocks them, and Guard reports each one; 2.0.0 said Chrome loads them.
- **For contributors:** when a test fails, `check.py` shows the failure's own lines (what was expected and what came), not only the end of the run.

## 2.0.0 (2026-10-11): the first public release

LibKa was developed in a private repository up to 2.0; this repository starts with it.

- **Documents:** one Markdown file with LibKa blocks (35 block types, from headings and lists to charts, diagrams and timelines) builds a web page, an A4 PDF, 16:9 slides and an editable Word file; each document chooses its outputs.
- **Guard:** every output is checked (axe-core WCAG 2.2 A/AA in Chrome, text contrast 4.5:1 and 7:1 in high contrast, structure rules, reflow at 320 CSS pixels, slide fit; veraPDF PDF/UA-1 for the PDF; the Word file's structure) and the outputs that pass are signed; a conformance report maps each WCAG 2.2 criterion to EN 301 549. A PDF built without veraPDF is marked as not validated in its manifest, its conformance report and `libka verify`.
- **LibKa Studio:** an installable, local-first web app with visual and source editing, live checks with quick fixes, versions, English and Czech; self-audited against WCAG 2.2 A/AA, with the evidence in `docs/acr/studio.md`. Help, About LibKa Studio gives the licence, the third-party notices and what happens to your documents; `build.mjs --hosted` builds a copy for a web address of its own, whose headers keep a host's statistics script out (`no-transform`); it starts offline on hosts that redirect `index.html` too.
- **Documentation:** the documents in `docs/` are LibKa documents themselves, from [getting started](docs/getting-started.md) to the conformance reports; the block registry carries a Czech example for every block. HTML comments are allowed in documents as notes for editors and are never rendered.
- **Design tokens:** W3C DTCG 2025.10 tokens with light, dark and high-contrast themes, generated into CSS, SCSS and Tailwind themes with contrast gates.
- **AI authoring:** an Agent Skill and an MCP server; AI-written content is checked like any other, and content the document declares as AI-written is listed in the signed manifest. For Claude Code both come as one plugin from this repository's marketplace file; for Claude Desktop the server comes as an extension (`.mcpb`), and the skill as a `.zip` for claude.ai and Desktop ([`docs/ai-tools.md`](docs/ai-tools.md)).
- **Packages:** `@libka/cli` (the `libka` command, with LibKa Studio), `@libka/mcp`, `@libka/tokens`, and `npm create libka` for a new project with an example in English or Czech, npm scripts and a CI workflow. `libka doctor` says what a computer has and what works without each missing piece; a wrong command, a missing value or a missing file is named, and a misspelled front-matter key gets the nearest known one. Each project signs with its own key, and trusts its first key in its own list.
- **Releases:** built from a tag by `publish.yml`: the npm packages with provenance (this first version's packages are published by hand, so they carry no provenance statement), the MCP server in the MCP Registry, and a draft GitHub Release with the Desktop extension, the skill `.zip` and SHA-256 checksums, published after review. Run by hand, the workflow is a dry run by default.
