# The Studio: build, serve, install, test, and where documents live

**What it is.**
- LibKa Studio is the authors' app (`apps/studio`): a visual editor and a source editor, apart or side by side, a live preview (web, phone, A4, slides), Guard's checks while typing, a library of documents, version history, and downloads (Markdown, HTML, slides, Word, zip).
- It is an installable web app (a PWA): a static folder, `apps/studio/dist/`, with a service worker that keeps the whole app in the browser's cache, so it starts offline once it has been opened.
- It needs no server of its own and has no account. Documents, their images and their versions stay in the browser that is used (IndexedDB), or in a folder on disk that the author picks.

**Three ways to edit.** Visual: the document as it looks, blocks as objects with their Properties. Source: the LibKa Markdown in CodeMirror. Split: both side by side, in step as the author writes (only the changed blocks or characters are replaced on the other side, outside its undo history, so each side keeps its own undo, scroll and place; the block being edited is marked on both sides). Split needs a window at least 1280 pixels wide; on a narrower one the document shows in Visual. The switch in the editor's toolbar changes between Visual and Source at any time, keeping the place; Split is chosen in View ▾ (and while it is on, the switch shows it too); new documents open in the mode chosen under View ▾ → Preferences. Switching never changes the text: blocks you did not edit stay byte for byte as written, and an edited block is written in LibKa's canonical style (`@libka/editor`). A block that holds blocks (`::::cards`, `::::decision` …) keeps its opening and closing lines, its untouched parts and the space between them at every level; only the edited part is written anew, and the opening line only when the block's own settings changed. Before it is used, the result is read back and must mean the block. If it does not (a fence that has grown too short, say), the fence is lengthened, and failing that the whole block is written canonically (`saveMapped`, `rewriteContainer`). The blank lines around an edited block are kept when they include an empty line. A list stays one unit: an edited item rewrites its list.

**Quick fixes.** Every source problem has a code (the list: [`docs/problem-codes.md`](../problem-codes.md)) and, where it is safe, fixes: a misspelt block or setting renamed, an unknown setting removed, a task list put in a checklist, a table put in `:::table` for its caption, a heading level or list type changed, the outputs corrected. They are offered in Checks, on the problem marks at the right of blocks in Visual (which open Checks on that block), and as actions on the problem's line in Source; each is one step the author can undo. A fix that needs the author's words (alt text, a caption, a title) never writes them: it takes the author to the empty field. Guard's findings are explained in plain words (why it matters, how to fix it, in English and Czech) with "Go to the text".

**The frame and the modes.** The app bar holds Documents, the open document's title as **Document ▾**, the save state, the mode switch, the check status, View ▾, Help ▾ and **Export ▾** (below). The modes: **Write** (Psaní, Alt+1) is the editor with the companion pane on Preview (A4 by default, scaled to the pane); **Blocks** (Bloky, Alt+2) opens the Catalog on the left and Properties on the right; **Focus** (Fokus, Alt+3, also Ctrl+Shift+F and the preference) is the page alone (below). Each mode remembers its own panes: which tab the left pane and the companion show, or that they are closed; the companion's width is shared. They are kept per browser (`localStorage`, key `libka-studio:layout`; `state/layout.ts`), never per document. The regions are landmarks: the app bar (banner), the rail (navigation "Left pane"), the left pane (complementary, Catalog or Outline), the editor (the one main), the companion (complementary, named after its tab: Preview, Checks, Properties, Versions while open, the Tutorial in the tutorial), the status bar (contentinfo). F6 and Shift+F6 move between the regions shown (changeable keys, like every command). The rail's buttons open the left pane on a tab or close it; a closed companion leaves a strip of its tabs at the right edge. The splitter between the editor and the companion is a WAI-ARIA window splitter: drag it, or Left and Right (16 px, 64 with Shift), Home and End (narrowest, widest), Enter closes the companion. **Checks** is one list (below); **Properties** is the former Inspector; the **Outline** lists the headings, and "Show every block" switches to the tree of blocks (the former Structure tab); the **Catalog** is every block with its drawing (click to insert, or drag in Visual) and replaces the side palette, whose preference is gone. Extensions add tabs with a `region` (`companion`, the default, or `left`); a tab with `keepMounted` stays rendered while hidden (the preview's frame, which printing and the checks' highlights use).

**Document ▾, Export ▾ and plain names.** **Document ▾** (the title) holds Rename… (one dialog with the title, written to the front matter, and the file name), Duplicate (the copy, with its files, is opened at once and announced), Save now (Ctrl+S), Save a version… (Ctrl+Shift+S), Versions… and Document properties; a menu row shows its command's keys (`aria-keyshortcuts` too), and a separator falls between the hundreds of the menu orders (`registry.menuGroups`). **Export ▾** (the primary button, only with a document open) replaces File ▾: Web page (.html), Slides (.html), Word (.docx), PDF (print…), LibKa Markdown (.md); Save to a folder…, Download everything (.zip); Choose outputs… opens Properties at the document's outputs, the one place they are set (`toggleOutput` in `core/outputs.ts`). New document, Open the example, Import and Open folder are the Documents view's buttons and palette commands. **Properties** names every setting in plain words in the interface language ("Next review", "Tab name"), with the key the Markdown uses small beside it and read as part of its description ("In the file: next-review"); the document's names are the Studio's texts (`field.*`), the blocks' come from the registry (`settingTitle` in `@libka/blocks`, `packages/blocks/src/setting-titles.ts`: one name per key, overridden per block or child where it means something else; a test keeps every setting named in both languages; the catalog shows them as "Name in the Studio").

**Focus, the layout in View, and phones.** **Focus** hides the panes, the rails, the editor's toolbar and the status bar; the text is a column of at most 760 px, a little larger (`visual.css`, `.st-work[data-focus]`). Under the page is a dock (`FocusDock` in `ui/Workspace.tsx`, a group "Focus"): **+ Block** (the block picker, opened above the dock when there is no room below), the **Checks** count (opens Checks and leaves Focus) and **Exit Focus** (back to the mode before Focus; Ctrl+Shift+F does the same, Alt+1 goes to Write). The dock is a row of the layout under the editor, never a layer over the text (WCAG 2.4.11). Esc stays the editor's (it selects the block); formatting stays on its keys. **View ▾** has the right pane's width as **Narrow** (300 px), **Medium** (the default for the mode and the window) and **Wide** (600 px), each kept within the window's limits when drawn (a resize without dragging, WCAG 2.5.7; the splitter still works), and **Reset this mode's layout** (the mode's panes as they come and the default width; announced). Both are palette commands too (`panes.narrow`, `panes.medium`, `panes.wide`, `layout.reset`; no default keys). Below 1280 px View ▾ is 214 px wide. **A menu never leaves a sliver:** an open list is drawn over the controls under it, and a click outside closes it and still reaches the control it lands on, so a control covered all but a few pixels would be a target under 24 px (2.5.8). When a menu opens, `clearSlivers` in `ui/Menu.tsx` moves its list sideways by the smallest step (at most 96 px, inside the window) that leaves every control under its edges either covered or with 24 px of its own; the width stays. The step is a rule in a style element, kept only while that menu is open (`#id[open]`), and measured again at each opening and on resize. Found at 1024 px (View ▾ over Source), under the Czech Document ▾ (Code) and under Help ▾ and Export ▾ (the Preview's buttons); tested in `visual.test.ts` ("opens the menus of the top bar …"). **Phones** (narrower than 900 px, `s.phone`): the app bar is one row, the Studio's dot, the readiness chip, Documents (its icon) and **⋯** (`MoreMenu` in `ui/TopBar.tsx`), which holds the line, the word count and the saving state at its top, then the modes, Document, View, Export and Help; a failed save shows in the bar itself (`#save-alert`). The regions are a bar at the bottom (`PhoneBar`, a navigation "Regions"): Write, Preview, Checks (with its count) and Outline, each opening one whole-screen region, 52 px tall with an icon and a name, clear of the home-gesture area (`env(safe-area-inset-bottom)`); it hides while the on-screen keyboard is open (`s.keyboardOpen`: the visual viewport is more than 120 px shorter than the tallest seen at this width while a text field has the focus). The status bar is not drawn on a phone or in Focus. F6 goes through the app bar, the left pane, the editor, the companion, the bottom bar and the status bar (`app/regions.ts`).

**The block bar.** `BlockBar` in `ui/Visual.tsx`, its target and setting from `@libka/editor`'s `bar.ts`: `barTarget` (the selected block when it is a registry directive or a figure, else the innermost one around the selection; a child such as `card` or `q` belongs to its block; plain text, headings, lists and tables have none), `quickSetting` (the attribute the registry marks `quick: true`, named and its values labelled in the language; a blocks test keeps it to at most one per block, a choice or a flag, on callout, decision, flow, matrix, chart, cta, summary, section, toc, references and ui), `barPartHolder` ("+ part": the part holder around the cursor inside the block, a pros-cons's `pros`, or the block), `setBlockAttribute` and `selectBlockAt`. The bar holds the block's name, the setting as a list (an optional one's empty value is "Default", since each has one; a required one has "(none)" only while missing), a figure's alt text as a button to its field in Properties ("Write alt text" with a dashed border, or "✓ Alt text done"), "+ Stage" (disabled at the limit, with the reason), Move up and Move down, ⋯ (the block menu, `blockItems`, for this block) and Properties. Move, ⋯ and Properties select the block first; the setting and Move dispatch without moving the focus, so a list changed by arrow keys or Move pressed twice keeps it. Placement (`where`): in the toolbar after + Block inside `.st-blockbar-slot`, which is inline when the editor pane is 1180 px or wider and otherwise a row of its own under the toolbar that stays while the cursor is in plain text (the toolbar's height never changes with the cursor); in Focus inside the dock; on a phone a row between the editor and the bottom bar, only while Write is the region shown. Not in Source. Tested in `packages/editor/test/bar.test.ts` (the editor: the target for every registry example, the setting, byte for byte) and `visual.test.ts` ("the block bar …").

**Present.** `app/present.tsx`. Two commands, **Present** (`present.start`, F5, from the first slide) and **Present from this slide** (`present.here`, Shift+F5, the slide the cursor is in), in View ▾ (so in the phone's ⋯), the palette and a Present button in the Preview's Slides view (from the slide shown there); the keys are changeable like any other. `present()` runs in the author's press itself: it asks the browser for full screen on the whole Studio (`document.documentElement`) and shows `PresentHost`, a modal `<dialog>` that fills the window, with the deck in a `srcdoc` frame (the Preview's deck, fitted, without its policy: the Studio's applies, as in the Preview). The Studio adds an **End** button (`#present-end`, "Esc") to the deck's bar, since a phone or touch screen has no Esc. `deckControls(win, where)` takes over the deck's own full-screen and presenter controls (its buttons, F and P with the letter shortcuts on) and F5 / Shift+F5 in a deck the Studio shows: in the Preview they start Present from the slide shown (P with the presenter view); while presenting, F toggles full screen and P opens the presenter view. **The presenter view** is the same deck opened from a `blob:` address in a popup (`window.open`; a frame cannot be `blob:`, the Studio's `frame-src` allows only its own origin and the two video players, but a window is not a frame), with a `<base>` to the Studio so its fonts and pictures load; the deck runtime's `libkaDeck.link(win)` pairs the two windows once both have loaded, and they keep the slide in step by `postMessage` as the exported deck's do. A browser gives one press one of the two: from the Preview's P the window opens and the deck fills the Studio's window instead of the screen (F makes it full screen). **Ending:** Esc in the deck once it has nothing of its own to close (overview, notes), the dialog's own Esc, End, or the browser leaving full screen (its Esc), except while the presenter view is open (the author may be moving windows between screens; then Esc or End ends it). The end closes the presenter view, leaves full screen, puts the Preview on the slide it ended on (`lastShown`, also for the Preview's next switch to Slides) and returns the focus where it was (the text, when the command came from a menu). **The cursor's slide:** with `sourceLines`, each slide's frame carries `data-lk-slide-line`, the source line of the block that started it (`Slide.line` in `@libka/render`'s `slides()`; continuations and the title slide none, `withoutLines` removes it with the block marks); `slideOfLine` picks the last slide that starts at or before the line (`selectedLine()`: the top-level block in Visual, the cursor's line in Source). Tested in `visual.test.ts` ("presents the deck …": View ▾, F5, Shift+F5, F, End, Esc, the Preview's P with the presenter window in step both ways, the Preview's last slide, Czech, Guard with the presentation open).

**Blocks that look like their output.** In the visual editor the blocks with a layout of their own are drawn in their output's arrangement, with its marks, by the editor's own CSS from the tokens (`visual.css`, "blocks in their output's arrangement"), not by the outputs' `components.css`: a matrix's quadrants two by two with its axes above and below, a flow's stages in a row (numbered, an arrow between them, ↻ under a cycle), pros beside cons and do beside don't (✓ and ✗), cards in a grid (a badge on top), key figures as tiles (the bold figure large), a timeline as dots on a line (the `current=` milestone filled and marked "Now"), steps as numbered circles. The block's name stays as the small label above. The editor pane is a size container: below 720 px a flow's stages stack, below 520 px the grids too. `@libka/editor`'s `parts.ts` says which blocks are laid out (`LAID_OUT`, `GRIDS`) and what each repeats (`LAID_PARTS`: list items or child blocks, the limits read from the registry's schema: six stages, four key figures; a matrix has no part to add), and `addPart` adds one at the end with the cursor in it (bold from the start when the last item opens with a bold figure or date). The node view (`directive` in `visual/view.ts`) adds the marks and a "+ Stage", "+ Card", "+ Pro" button at the block's end (hidden at the limit); the block menu (Shift+F10) has "Add: …" for the keyboard, disabled at the limit with the reason. A grid's parts get their handle inside them, at the top right corner, since a grid would place anything beside its parts in its first cell; the blocks inside a part have none (Esc selects them). An edit inside a container block changes only the edited part, as in "Three ways to edit" above. The other blocks drawn this way: each tab's label underlined as a tab over its panel, all panels shown and editable ("+ Tab"); an accordion's items as rows with ▾ and the answer under the question ("+ Item"); a comparison's `highlight=` column outlined with its badge (`badge=`, or "Recommended" in the interface language) and yes, no and partial cells marked (decorations, `comparisonMarks` in `visual/view.ts`); a decision's status (its value label from the registry, a coloured dot), date and `by` as a line above it, its context, options and consequences as ruled sections; a release's date, each kind of change ruled in its colour; a UI specimen's caption, then its components drawn as components (a button by its variant, a field with its box, a badge as a pill), in a row or stacked (`layout=`), a state shown by its shape (⊘ disabled, … loading), never by fading. A specimen's components have no handles (they sit in a row; a click or Esc selects one).

**One Checks list.** Checks merges the source problems, Guard's findings in every output and the lint hints (`ParseResult.hints`) into one list by place: the document's properties first, then each top-level block under its section ("Before you start › Figure"), then what could not be placed ("The whole document"). Each item is tagged with where it fails (Source, Web and PDF, Slides, Word) and its kind: **Must fix**, or **Advice** for a hint, which never counts and never stops anything. One item per block and rule across outputs: the same finding on the web page and the slides is one item, and a source problem and Guard's finding of the same thing (alt text, a caption: the `SAME` table in `core/checklist.ts`) are one item with the problem's fixes. The readiness chip and the tab count items to fix, not findings. A finding is placed on its block by the source line the Studio's render marks on every top-level block (`sourceLines` in `@libka/render`, `sourceLine` in `@libka/model`; Guard's scan reads it as a finding's `line`, the Studio maps axe's selectors itself); a Word finding by the text it quotes. The marks exist only in the Studio: `libka build` never writes them, exports strip them (`withoutLines`), and a render test proves the page without them is the build's byte for byte. The filters are All | This block (the block with the visual editor's selection, or Source's cursor); a block's "!n" mark opens Checks on that block with the focus on its first fix, and Properties shows the block's count with "Show in Checks". Each item goes to the text; a finding in the web page or the slides has "Show in the preview" (the output, the contrast mode and the slide it is on, outlined). The checks' own numbers, as `libka check` reports them, are under **Details: the checks of each output**, an output with findings unfolded.

**The calm default.** View ▾ holds dark mode, high contrast, the interface language, Split and Preferences. The editor has one toolbar row in a fixed order in every mode: the format buttons, **+ Block** and the Visual | Source switch. In Source the format buttons stay in place, unavailable, with the reason under them (the formatting is written in the Markdown there). **+ Block** opens the block picker: search in English or Czech, the recent blocks first, the groups, a small drawing of every block (`apps/studio/src/ui/thumbs.tsx`), a close button, and a click outside closes it; in Visual the same picker opens with "/" on an empty line or Ctrl+Shift+Enter at the cursor. It inserts in either editor: a block object after the selected block in Visual, the block's Markdown at the cursor in Source. The versions inside (tokens, axe-core, the build) are under Help → About → For developers, not on the status bar. Help text from the registry is shown without its Markdown marks (`plainText` in `@libka/editor`).

**The command palette.** Ctrl+K (Cmd+K on a Mac) or F1 searches commands (with their keys), blocks to insert, places in the document (headings and titled blocks), settings and the library's documents, in English and Czech, accents optional. Ctrl+K on text selected in either editor makes a link instead. The keys of the Studio's commands can be changed under View ▾ → Preferences → Keys of the Studio's commands (Backspace removes one, Default goes back; keys the editors or another command use are refused and named); they are kept per browser (`localStorage`, key `libka-studio:keys`).

**Czech throughout.** With CS chosen, block names, summaries and the help of every setting come from the registry's Czech text (`packages/blocks/src/i18n.ts`); value labels are shown next to the values the Markdown keeps (`warning` stays `warning`). The catalog, the AI skill and the MCP server stay English, and so do the source problems' messages (their codes and fixes are the same in both languages).

**Onboarding.** On the first visit a short tour points at the parts of the Studio (non-modal; Escape or "Skip the tour" ends it; Help → Take the tour shows it again). It ends by offering the tutorial (Help → Open the tutorial): a document in the interface language (`apps/studio/tutorial/`) with a Tutorial tab whose nine steps tick themselves as the author does them, ending when the document is ready to publish and has been exported. The tour's "seen" mark is `libka-studio:toured`; the tutorial's progress is `libka-studio:tutorial`, per document.

**Preferences** (View ▾ → Preferences, kept per browser): block handles always or on hover, Markdown shortcuts, text on buttons or icons only, spacing, Focus (Ctrl+Shift+F), typewriter scrolling, the mode of new documents (Visual, Split or Source), short or full screen-reader messages, and the keys of the Studio's commands. Help → Keyboard shortcuts (also "?" on a selected block, or Shift+Alt+H) lists every key, with the author's own. The preferences are saved whole with a version (`v` in `libka-studio:editor`); a version step applies a changed default once to everyone (version 2: the side palette off; its key is now dropped, since the Catalog replaced it).

**Accessibility.** The Studio itself is audited against WCAG 2.2 A/AA: `apps/studio/audit/audit.ts` lists every criterion with its result and evidence, `node apps/studio/audit/build-acr.ts` writes the report `docs/acr/studio.md` (a test fails when it is stale or cites a test that does not exist), and Help → Accessibility shows a short statement with the same numbers and limits. Screen-reader tests with NVDA run on request: [screen-readers.md](screen-readers.md).

**Content Security Policy.** The Studio runs under its own strict policy: scripts only from its own files plus, by hash, the two inline runtimes its previews carry (a web page's and a deck's, in English and Czech); no `eval`, no inline handlers; inline styles allowed (the Studio places popovers with them, and Mermaid styles its diagrams; styles run no code). The build computes the policy (`dist/csp.txt`), writes it into `index.html`, and `libka studio` also sends it as a header with `frame-ancestors 'none'`. The previews are `srcdoc` frames, which take the Studio's policy over; the code the Studio runs inside them (Guard's scans, slide measuring) is `assets/frame-agent.js`, loaded as a file and called by name. The runtimes' text is generated (`node packages/render/src/build-runtimes.ts`, a test fails when stale), so the minified Studio writes exactly the scripts the policy names.

**Performance budget.** Tests fail (`apps/studio/test/performance.test.ts`) when the Studio is over a budget: first load (main.js and studio.css) 1.5 MB (the build fails too), ready to edit 2 s, a keystroke 50 ms (95th percentile) in the 27-page Open Source Guide, the checks back 5 s after typing stops, the guide's 90 slides laid out again 10 s after an edit. `LIBKA_PERF_SLACK` multiplies the time budgets on a slower machine; CI sets 2. The tests print the numbers either way.

**Why it is served over http.** A service worker (offline start, installing as an app) works only on an http address (localhost counts) or https, never on a file opened from disk. `libka studio` serves the folder on your machine; the hosted Studio serves the same folder.

## Build and run

1. **Build:** `node apps/studio/build.mjs`. It writes `apps/studio/dist/` and prints the Studio's version (a hash of everything built), the number of files and the size of the first load. The same sources always give the same files.
2. **Serve:** `node packages/cli/src/libka.ts studio`. It prints the address, `http://localhost:5178/`. Open it in Chrome, Edge, Firefox or Safari. `--port <n>` chooses another port; `--dir <folder>` serves another build. Ctrl+C stops it.
3. **Install as an app (optional):** in Chrome or Edge, the install icon in the address bar (or the menu, "Install LibKa Studio"). It then opens in its own window and from the Start menu. Uninstall it from the app's own menu.

After a rebuild, an open Studio shows "A new version of the Studio is ready" with a Reload button; the new version takes over when the author reloads. Nothing is lost: the text is saved as it is typed.

**A hosted copy.** `node apps/studio/build.mjs --hosted --publisher <file> --out <folder>` builds the copy for a web address of its own (its own origin, so no other site's script can reach the documents people keep in it). Its Help, About LibKa Studio names who provides it, with links to their site, imprint and privacy policy, read when it is built from the JSON file `--publisher <file>` names (its `public` block: `copyrightHolder`, `siteUrl`, `imprintUrl`, `privacyUrl`, and `githubOwner` for the link to the source; the file stays with the publisher, never in a repository); the build says which of them is missing. It also writes `_headers` for the host: the Studio's Content Security Policy with `frame-ancestors 'none'`, no referrer, `nosniff`, HSTS, a Permissions-Policy, and `Cache-Control` with `no-transform` (so a host cannot add a statistics script to the pages). A host may answer `/index.html` with a redirect to `/` (Cloudflare does); the service worker serves such an answer as a plain one, because a browser refuses a redirected answer to a page load. Every build, hosted or not, has the About dialog (the version, the licence, the third-party notices, the source when the build knows it, what happens to your documents) and no analytics.

## Where documents live

:::table{caption="Where the Studio keeps documents and settings, and for how long"}

| What | Where | How long |
|---|---|---|
| Documents (one LibKa Markdown text each), their images, their versions, the folders they are linked to | IndexedDB of that browser, database `libka-studio`, for the address the Studio was opened on | until the author deletes them, or the browser's site data for that address is cleared |
| Interface choices: language, theme, contrast, the last open document, editor preferences, the keys of commands, the tour seen, the tutorial's progress | `localStorage`, keys starting `libka-studio:` | the same |
| A copy on disk | a folder the author picked (Chrome and Edge), or a downloaded `.zip` | the author's own files |

:::

- **The address matters.** `http://localhost:5178/` and `http://127.0.0.1:5178/` are two different sites to the browser, with separate documents. Always use the address `libka studio` prints.
- **The Studio asks the browser to keep its storage** (persistent storage), so the browser does not clear it when the disk runs low. Clearing site data by hand still deletes it.
- **Private windows** may give no storage at all. The Studio then says so in the library and works in memory only; the work is lost when the window closes unless it is downloaded as a zip.
- **Versions:** after a pause in typing (at most every 5 minutes), before anything replaces the text (opening, a restore, reloading from a folder), and whenever the author saves a named version. The last 50 automatic ones are kept per document; named ones always.
- **A folder** has exactly the layout `libka build` reads: the Markdown file and the images it uses at the paths it names. "Open folder" on a folder already linked to a document reloads that document from disk (the text before stays in the history). Folders work in Chrome and Edge only; other browsers use the zip.

### Clearing the Studio's data on one machine

In Chrome or Edge: open the Studio, then the padlock or site icon in the address bar → Site settings → Delete data (or DevTools → Application → Storage → Clear site data). Firefox: Settings → Privacy → Manage Data. This deletes every document kept there; download what you need first.

## Tests

- `npx --yes pnpm@12.8.1 --filter @libka/studio test` builds the Studio once (the global setup in `vitest.config.ts`), then runs:
  - unit tests of storage, versions, zip, folders, the comparison, the outputs, the command registry, the saved layout and the merged Checks list (`test/storage.test.ts`, `test/core.test.ts`; IndexedDB is faked in Node);
  - Chrome tests of the app served on localhost (`test/studio.test.ts`): Guard on the Studio's own views, the same Guard counts as the CLI, persistence across reloads, images, undo, versions and the comparison, zip, folders, starting offline, the move of the old draft;
  - Chrome tests of visual mode (`test/visual.test.ts`): the Markdown kept byte for byte, keyboard-only editing (select, climb, move, extend, duplicate, delete, undo, announcements), the "/" menu, Properties, inline keys and badges, the handle menu and the Catalog (click and drag), the Outline and its tree, the preferences and Focus, the shortcut list, restoring a version, and Guard on every view in standard and high contrast;
  - Chrome tests of Split, fixes and the palette (`test/split.test.ts`): Split in step both ways with separate undo, Split on wide screens only, every text fix kind from Checks with its undo, CodeMirror's fix actions, problem marks and fields to fill in Visual, Guard findings explained, the command palette and its sources, links on selected text in both editors, changing the keys of commands, Czech, and Guard on the new views;
  - Chrome tests of onboarding (`test/onboarding.test.ts`): the tour by keyboard (first visit, skipped, again from Help), the tutorial done end to end until it is exported, both languages;
  - Node tests of the palette's places, the keys of commands, the Guard explanations (every rule, both languages) and Split's minimal change (`test/switchable.test.ts`);
  - Chrome tests of quality (`test/quality.test.ts`): the Studio under its own policy through a whole workflow, forced colours, text-field contrast, reflow at 320 px, text spacing, the focus never hidden, names and visible labels, the window title and the document's language, About LibKa Studio, the accessibility statement, the regions (landmarks, F6, the splitter, the modes' keys, two columns at 1024 px), Focus's dock and View's widths and Reset, the phone (one app-bar row, ⋯, the bottom bar and the on-screen keyboard, 320 px), and touch on a tablet and a phone;
  - the performance budget (`test/performance.test.ts`) and the accessibility audit's consistency (`test/audit.test.ts`);
  - screen-reader tests with NVDA (`test/screen-reader.test.ts`), on request only: [screen-readers.md](screen-readers.md);
  - smoke tests in Firefox and WebKit, Safari's engine (`test/browsers.test.ts`): the tour skipped, editing in both modes.
- The tests set the cursor with `window.libkaStudio.placeCaret(text)`, a hook for automation (`window.libkaStudio.sides` gives the text on each side of a Split); the keys under test are pressed for real. The older tests in `test/studio.test.ts` drive the source editor and set "new documents open in Source" before the page loads. Every test except the onboarding ones marks the tour as seen first (`libka-studio:toured`), since the tour takes the focus on a first visit.
- **Firefox and WebKit for the tests** are Playwright's own builds, not browsers you browse with: `npx playwright-core install firefox webkit`, run in `apps/studio` (about 190 MB to download and 520 MB on disk, no administrator rights). They go into Playwright's browser folder: `%LOCALAPPDATA%\ms-playwright` by default, or the folder the environment variable `PLAYWRIGHT_BROWSERS_PATH` names; `npx playwright-core install --dry-run` shows where each build goes. Each `playwright-core` version needs its own builds, so install them again with the same command after an update; older builds stay in the folder until you remove them. Without them the smoke tests are skipped with a message; CI installs them and sets `LIBKA_REQUIRE_BROWSERS=1`, so a missing browser fails there. To check an installation, run `test/browsers.test.ts` with `LIBKA_REQUIRE_BROWSERS=1` too.
- **Folders in the tests:** Chrome's tests stand a folder in the origin private file system in for one the author picks. Chrome crashes when it reads such a handle back from IndexedDB (an ordinary picked folder is fine), so the test wraps it in a plain object.

## When something fails

:::table{caption="Studio problems: symptoms, likely causes and what to do"}

| Symptom | Likely cause | What to do |
|---|---|---|
| `libka studio` says there is no Studio | not built | `node apps/studio/build.mjs` |
| `port 5178 is in use` | another `libka studio`, or another program | stop the other one, or `--port 5179` (note: a new port is a new site with its own documents) |
| The Studio shows an old version | the service worker serves its cache until the author reloads | use the Reload button in the notice, or reload twice |
| "Not kept: this browser gives no storage" | private window, or storage blocked for the site | use a normal window; download the work as a zip |
| "Saving to … failed" or "did not allow writing" | the browser's permission for the folder expired or was refused | Save to folder again and allow; or download a zip |
| The Studio's own Guard test reports `no-inline-style` | a style attribute outside the editor | the Studio writes no style attributes; CodeMirror's geometry inside `.cm-editor` is the only exemption |
| Firefox or WebKit tests skipped | Playwright's browsers not installed | `npx playwright-core install firefox webkit` in `apps/studio` |
| A test types into the wrong place right after closing a dialog | the dialog's close event came after the next step | wait until the dialog is gone (`waitForSelector('dialog', { state: 'detached' })`) before the next key |
| A Split button is missing | the window is narrower than 1280 pixels | widen the window; the document shows in Visual meanwhile |
| A command's key does nothing | the author changed or removed it | View ▾ → Preferences → Keys of the Studio's commands → Default |
| A preview stays blank, or the checks never finish, and the console says "Refused to execute" | a page runtime changed but its text was not regenerated, so the policy does not name its hash | `node packages/render/src/build-runtimes.ts`, then rebuild the Studio |
| "the frame agent did not load" in the console | `assets/frame-agent.js` is missing (an old or partial build) | `node apps/studio/build.mjs` |
| A performance test fails on a slow machine | the budgets are set for a developer machine | close other programs, or set `LIBKA_PERF_SLACK=2`; on a fast machine, look at what got slower |
| The build stops: "the first load is … over the budget" | new code in the first load | load it when it is needed, with a dynamic `import()` |

:::
